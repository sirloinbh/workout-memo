# UI/UX audit — 2026-10-21

This is the result of [#112](https://github.com/sirloinbh/workout-memo/issues/112). The app is used mainly on a phone and only occasionally on a PC. So we ran the task scenarios on a 390px screen and took 1280px screenshots for comparison. The improvements are linked to follow-up issues such as [choosing the UI standard #98](https://github.com/sirloinbh/workout-memo/issues/98) and [mobile input flow #105](https://github.com/sirloinbh/workout-memo/issues/105).

## Method

- Target: `origin/main` `2058660` (when #97 was merged). The personal DB was not used.
  - We created a new audit DB, `workout_ux_audit`, in a local-only test DB container.
  - We applied the schema with `npm run db:migrate`.
  - We started the API (3101) and Vite (5174) the same way as e2e.
- Data: we seeded it through the API.
  - 12 logs over the last 4 weeks: a 3-way split of lower body, chest and back; 9 exercises; 108 sets
  - 2 goals, 4 body records (once a week), 1 machine
  - In scenario 1 we added one more log through the screen.
- Tool: Playwright (installed Chrome)
  - Screen sizes: 390×844, 1280×800
  - For each page we measured the following.
    - Horizontal overflow (`scrollWidth`)
    - Touch targets under 44px
    - Input text under 16px
    - Text under 13px
    - Page and modal height
- Criteria: heuristics (Nielsen's 10 principles)
  - Mobile touch targets of 44px, input text of 16px or more (to prevent iOS zoom)
  - Whether the main action is visible on the first screen
  - Empty states and how the save result is shown
- What we could not do
  - Testing on a real phone
  - Lighthouse mobile: the Lighthouse run in the DevTools MCP did not respond for 30 minutes, so we stopped it.
  - We continue both items with the [re-measuring](#re-measuring) procedure.

## Re-measuring

After the UI replacement (#101 to #105), measure again under the same conditions and create a new dated document that compares with this one.

1. Create an audit DB in the test DB container and run `npm run db:migrate`. Do not use the personal DB.
2. Run `tsx backend/src/server.ts` with `DATABASE_URL` set to the audit DB and `PORT=3101`.
3. Run `npm run dev -w frontend -- --port 5174` with `API_PROXY_TARGET=http://127.0.0.1:3101`.
4. Insert the seed set above (12 logs over 4 weeks, 2 goals, 4 body records) through the API.
5. Run the 6 scenarios at 390×844 and measure the same metrics.
6. Run scenarios 1 and 2 on a real Android phone and write down the device and browser. The production server has an IP restriction, so connect from Wi-Fi on an allowed IP.
7. Record the accessibility and best-practices scores with Chrome DevTools Lighthouse (mobile).
